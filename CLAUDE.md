# SG_360review

SaaS-сервис оценки сотрудников по методу 360°. Мультитенантный, доменно-нейтральный.

## Стек
- Backend: Python 3.11+, Flask, Jinja2
- Frontend: серверный рендеринг + HTMX (без SPA, без React)
- БД: PostgreSQL, миграции через Alembic
- Диаграммы: Chart.js (CDN) на странице отчёта
- Фоновые задачи: APScheduler
- Деплой: Railway (регион EU), автодеплой из GitHub
- Платежи: ЮKassa
- Экспорт: openpyxl (XLSX)

## Источник правды
- Полное ТЗ — `docs/SG_360review_TZ.md`. Это источник правды по схеме БД, ролям, анонимности, жизненному циклу цикла и отчётам. Сверяйся с ним перед любыми изменениями модели данных. Если решение расходится с ТЗ — сначала спроси.

## Архитектура и инварианты
- Мультитенантность: каждый запрос скоупится по `company_id` из сессии админа. Никогда не отдавай данные другой компании — проверяй принадлежность на каждом запросе к БД.
- Доступ оценщиков — без аккаунта, по токен-ссылке `secrets.token_urlsafe(32)` на каждый assignment.
- Результаты цикла видит ТОЛЬКО админ.
- Снимок вопросов на цикл (`cycle_questions`) фиксируется при запуске — правки шаблона компетенций не должны менять прошлые отчёты.

## Правила анонимности (критично)
- `self` и `manager` — НЕ анонимны, показываются как отдельные источники.
- `peer` / `subordinate` — только агрегат и только если ответивших >= `companies.anon_threshold` (по умолчанию 3). Иначе группу скрывать с пометкой о недостатке ответов.
- Открытые ответы peer/subordinate — без привязки к автору, в перемешанном порядке.

## Конвенции кода
- Прямой читаемый код, без лишних абстракций.
- Все SQL — параметризованные.
- Секреты только из переменных окружения. Никогда не коммить `.env` (он в `.gitignore`).
- Комментарии и сообщения коммитов — по-русски, кратко.

## Деплой и окружение (Railway)
- Переменные окружения на Railway добавляются ПО ОДНОЙ через "New Variable". Не склеивать многострочные/составные значения — это даёт тихие баги.
- Хостинг строго EU.
- После изменений: прогнать локальные проверки → `git commit` + `git push`; Railway деплоит автоматически.

- Если появится вызов LLM — ответ может прийти в markdown-заборе ```json: извлекать перед парсингом.
- Внешние API: экспоненциальный backoff на rate limit.

## Рабочий процесс
- Перед крупными изменениями — показать план (Plan Mode), дождаться подтверждения.
- Делать по одному этапу из ТЗ (раздел 11 «Этапы реализации») за сессию, коммитить между этапами.
- После каждого этапа — краткий прогон/тест, показать что проверено.
